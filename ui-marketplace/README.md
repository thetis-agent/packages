# @thetis/ui-marketplace

The Extensions place of the web gateway, and the **Updates ready** card every page carries. The place is one card per extension family in the sections a person reads first -- **Needs your attention** (a to-do strip, only when something needs doing), **Installed** (with the pills **All · Installed by you · Given to you · Customized**), **Discover** -- and two folded ones, **Drafts in your folder** (only when there are some) and **Part of Thetis**, with one page per extension: its label, a publisher line ("by Thetis · Tools"), at most two chips, the one reason it needs a look, and **Install** (or **Use instead**), **Installed ✓ ▾**, **Update** or **Use Thetis's version**. Every chip, sentence and rule comes from `lib/state.js`, one state per extension, which `@thetis/ui-admin` mirrors so the Control panel says the same thing. The card tells every person, admin or not, when an extension they have has an update, applies it with one button without ever cancelling a reply, and applies the changes an agent made to the person's own extensions by itself when the reply ends; while the place is open it stays away, because the place's status line says the same. It is a `ui` package with no build step; its one dependency is the `@thetis/marketplace` library, for reading the index and the README copies and for `behind()`. Its browser modules run in the page; its commands run inside the person's own fence, where `@thetis/gateway-web` calls them as the person. Every person gets it by default. The place's id stays `marketplace`, so links to it keep working.

## What it provides

The manifest declares `type: "ui"` and a `ui` block with `dir: "ui"`, `entry: "index.js"` and `style: "index.css"`.

| Slot | Id | Label | Order | Hint |
|---|---|---|---|---|
| `places` | `marketplace` | Extensions | 20 | Add, update and remove extensions |

Thirty-three commands. The first eighteen may be sent by any signed-in person and work on the person's own packages, and the catalog of system packages on disk, through `env.kernel.packages`, their own configuration layer through `env.kernel.config`, their own fence through `fence.reload`, or -- for the three publishing verbs -- another installed package's tool through `env.invokeTool`; the last fifteen carry `role: "admin"` and go through `env.kernel.operator.call`. Seven of those are the Registries page's, in `lib/registries.js`. The manifest also carries `thetis.label` (`Extensions screen`, so its card in Part of Thetis is never read as the place itself) and `thetis.summary`, the name and the plain line the card and the store use for this package.

The gateway answers `403` to an admin verb from a user before the package's code runs, and the kernel refuses an operator method from a fence whose user is not an admin, with one exception it allows anyone: `fence.reload` naming the caller's own id, which is what `fence-reload` sends.

One configuration key, `applyOwnChanges` (`"auto"` or `"ask"`, default `auto`, settable by each person): whether the changes to a person's own extensions apply by themselves when a reply ends.

## Use

**Extensions** in the sidebar's ≡ menu, after **Control panel**, opens the place in the main pane. Escape or the close button returns to the conversation.

**The Updates ready card.** `install(ext)` starts one updater (`ui/updates-notice.js`), which asks `updates` when the page opens, when the tab becomes visible again, when the last running reply ends (`ext.turns.onIdle`), and every ten minutes. While a reply is running it asks nothing and never shows or changes a card. It draws up to three cards through `ext.notice`:

- `updates`: **Updates ready** · "Updates for 3 extensions: Web Gateway, Compaction and Skills." (the labels the cards say, Title Case, the newest version's) · **Review** (the place with `{ view: "updates" }`, at Needs your attention) · **Update all**. While the place or an extension's page is open (`updater.hold()`) the card is not drawn: the status line and the to-do strip say it. Update all fetches each `install` item in turn with progress on the card (a failed fetch is named at the end and the rest go on), then applies once: `fence-reload { drain: true }`, "Applying… a few seconds, your conversations are kept" (or "Pausing your reply at a safe point… it continues afterwards" when a reply is running), `ext.awaitReturn()`, and `location.reload()`, after which the new page says "Updated: …" in one toast. The sentence crosses the refresh in `sessionStorage`. When terminal sessions are open it asks once, on the card: "Update now? 2 terminal sessions will close. Conversations and files are kept." If the space does not come back in 90 seconds the card says "This is taking longer than usual" with **Try again**. A copy the official version moved past is never an item: that is the person's Review, not an update.
- `updates-own`: the person's own changes. When a reply has just ended, nothing else runs, no terminal is open and `applyOwnChanges` is `auto`, they apply by themselves and the card says "Applied your changes to moo." (the page refreshes only when the extension has page code). Otherwise it says **Changes ready** · "Your changes to moo are ready to use." · **Apply**. Opening the page or returning to the tab never applies anything by itself, and one set of changes (named by each package's newest change time) is applied automatically once per tab: if it is still there afterwards the card offers the button instead of looping.
- `updates-forks`: "Your changes are in the official version" (or "Your copy has no changes") · **Use Thetis's version** (**Use the original** for a copy of a person's extension), which unforks each copy (the files stay), waits for the gateway if the copy was the web gateway, then applies.

× on any card hides it until its set changes (`localStorage`, a per-viewer convenience; the place still shows the truth). Every storage access is wrapped, so a private window only loses the convenience. The card never sends `force`. An older page without `ext.notice`, `ext.turns` or `ext.awaitReturn` still works: no card, running replies read from the turn events, and the return waited for by asking `updates` until it answers.

When several registries offer the same package, the gallery takes the newest version, keeping the configured registry order for a tie. Its version, source and README come from that same offer.

**Three facts, said apart.** A row used to carry one word, `scope`, for what are three separate things, and that is how **Only me** came to sit on a package shipped with the installation and **Available** on one a person could not install. Now `system` says whose the package is: the installation's, shipped in the checkout or promoted into it, linked already built, and open to anyone by name -- the kernel's `install` takes a `@thetis/<name>` from any signed-in person, because the installation vouched for the code by shipping it and the link runs in the person's own fence. `installed` says whether it is in this person's workspace. `everyone` says whether every person gets it by default, and `everyoneBy` who decided that: `config` (the `systemPackages["*"]` list), `promoted`, or `marked` (an admin's mark, the only one a page can take back). A registry's offer that is also on disk here -- which on an installation whose registry is the repository the checkout ships is nearly every offer -- is one row, a system row, so an install of it is a link and never a clone.

**One state per extension** (`lib/state.js`, pure and exported; `ui/state.js` is a byte-identical copy, held by a test, because a page may import only its own files). `stateOf(row, { admin, origin, label, user, superseded, giver })` answers `{ chips, attention, reason, tone, waiting, update, behind, setup, todo }`: at most two chips from `CHIPS` in the order `CHIP_ORDER` -- **Needs setup** (red), **Update available** (amber), **Customized** (neutral), **For everyone** (blue, on something the person does not have only for an admin), each with its tooltip -- `attention` when something installed needs setup or has an update, `reason` the one sentence the page's banner says in `tone`, and `todo`, the row of **Needs your attention**: `update` [Update], `setup` [Set up], `optional` [Set up] -- something given to everyone (or to the person by an admin) that needs their own setting, neutral: "bitmuse gave everyone Notion. Set it up if you use it, or remove it for yourself." -- or `review` [Review]. **Update available** is only a real newer version of what the person runs (`updateOf`: never two equal versions, never a copy), and when the newer version renamed it the sentence ends "Now called <new>.". A copy the official version moved past is `behindOf`: **Customized**, and the Review row "Thetis's 0.4.1 is newer than your copy (made from 0.3.3).". The setup sentence is built from each key's help (`nounOf`, `setupSentence`): "Exa Web Search needs an Exa API key before it works. Get one at dashboard.exa.ai." -- a short noun, the help's link (never an example), never the key's name, nothing about `.env`, and the key's name as words ("an API key") when the help gives nothing. A problem only an admin can fix -- a `${VAR}` a default or the admin's layer refers to that is not in the server's environment, or a key declared `scope: "system"` -- is for anyone else the grey line "Waiting for your admin to finish setting this up" and never the chip; for an admin it is **Needs setup** with where to fix it. `publisherLine(row, { user, family })` is the line under every name: `by Thetis`, `by you` (authorship only: the person's namespace or a copy under their home), `by <person>` (a shared copy says whose original it was made from), or `from <registry>`, then ` · ` and the first two of `Tools`, `Skills`, `Page`, `Models`, `Background` (`KINDS`); `publisherShort` is the same for a confirm's `from` row ("Thetis · Tools"); `givenLine` is "Given to you by <admin>" for what an admin installed for the person. `labelOf` is the one Title Case label -- the newest version's, which `lib/rows.js` puts on the row -- and a copy with no label of its own reads as its official member while a variant with its own (`isVariant`: "Notion (Read Only)") keeps it and is never Customized. `summaryOf(row, origin)` is the one plain sentence every card and page opens with: the manifest's `thetis.summary` (a copy without one reads its official member's), else a plain line for one of Thetis's parts (`PART_SUMMARIES`), else the description's first sentence; the description itself is on Details. `bringsOf` is what it brings, from the same kinds as the publisher line, so "Tools · Skills" reads "7 tools · 12 skills" under it. `titleOf` is a page's title: the original of a shared copy reads "Notion — your original" ("Notion — bitmuse's original" for anyone else). `familiesOf(rows)` makes one family of an original, its copies (by `forkedFrom`) and a shared `@thetis/<n>` made from an `@<person>/<n>`; `headlineOf` picks the member the card shows, and `otherVersions` the page's lines, the one in use first even on its own page ("✓ Notion — you use this (shared with everyone)", "○ Notion — your original, in your folder", "○ Notion (Read Only) — a variant in your folder", each with its action, `use` or `install`); a person who is not an admin is never offered somebody's original of a shared copy ("○ Notion — bitmuse's original (same tools)", no button). `switchTitle` is the Use instead confirm's title ("Switch to your original Notion?"). `everyoneActions(row, { family, user, holders })` is the admin's decision table for everyone, the same on both surfaces: the lines ("Shared with everyone from Notion by bitmuse on 27 September 2026. Your people get this one.", "Already shared with everyone as Notion.", "Only admins can have this.", "Runs inside Thetis itself.", "Everyone gets it (set in Server settings).", "Only you have this. Use Remove for me."), the acts (`turnOn`, `turnOff`, `share`, `removeEveryone` -- the last only when somebody besides the reader has it) and their hints; beside Remove for everyone on a shared copy, "Sharing can't be stopped yet; Remove for everyone takes it from the people who have it now." A person's own copy of an older official version says "You can share your copy once it is based on Thetis's 0.4.1." `isRequired` (`REQUIRED`) is what nothing removes; `isAdminOnly` (`ADMIN_ONLY`: `thetis.audience: "admin"`, the types `host` and `storage`, `@thetis/gateway-login`) is what a non-admin is never offered; `runsInsideThetis` (`INSIDE`: host and storage, and a gateway, service or provider the person does not have) is nobody's to install. `matches(row, q, kind)` searches name, label, description, tool names, keywords and skill names; a synonym (`SYNONYMS`: web ↔ internet ↔ google) counts only as a word of the names, never inside a description. `placeSections(rows, { user, admin, superseded, q, kind, pill })` sorts the families into the place's sections, with `updates` (the Update rows' names), `counts` -- the unnarrowed numbers, `installed` being the one the Control panel says too -- `found`, the pills' numbers as the search and the type leave them, and `hidden`, the labels a pill hides from a search; the to-do rows come updates first, then setting up, then reviews, each by label, and a search puts a name match first (`matchRank`). The pills are `PILLS`: **Installed by you** (`mine`) is what the person installed themselves, **Given to you** (`given`) what an admin gave (everyone's defaults, what was turned on or shared for everyone, what an admin installed for them). `WORDS` holds the fixed sentences.

**The agent's name.** An admin may rename the agent in Control panel > Agent, so "Thetis" in the sentences quoted here is the default, not a fixed word. `lib/state.js` exports `useAgentName(fn)` and `agentName()`: the entry (`ui/index.js`) calls `useAgentName(() => ext.agent?.name || "Thetis")` first thing, and every sentence that names the agent -- "Part of Thetis", "Required by Thetis", "Runs inside Thetis itself", "by Thetis", "Thetis's version", "Use Thetis's version", the parts' plain lines -- reads `agentName()` when it is drawn, never at import, so the next draw says a new name. `agentName()` is "Thetis" when nothing was given, when the gateway has no `ext.agent` (an older one) or when the name is blank; the server never sets it. Identifiers keep the word: `who: "thetis"`, the `thetis` section, `runsInsideThetis`, `@thetis/...` names and the `thetis` command.

**Registries**, for admins, is a button at the end of the gallery's toolbar and a page of its own (the place opened with `{ view: "registries" }`), with the crumb **Extensions › Registries**. The button is drawn only where `ext.can("registries")`, which is the gateway saying the person's role clears the admin verbs; the verbs themselves answer 403 to anybody else and the kernel refuses the operator calls from a fence that is not an admin's, so hiding it is manners and not the lock. A registry without a key says it is read without credentials and offers **Add a key**: *Generate a key* (the host makes an ed25519 key for this repository) or *Paste a private key* (a deploy key that already exists, sent once and never drawn again). **Add registry** at the top opens the same choice under *Authentication: None | SSH key*, with the url and an optional name (the url's last segment when empty). Once a key exists the card shows its fingerprint, the public half in a read-only box with **Copy**, the line *Add this as a read-only deploy key* -- a link to the repository's deploy keys page when the host is github.com, worked out on the server, since the page parses no urls -- and **Test**, which answers `read` and the HEAD commit, or `refused` and git's own error. **Revoke key** takes the key away with the same keep-the-file tick. A key held for a repository that no registry names any more is listed under **Keys without a registry**, with **Revoke**, rather than left unseen.

Authentication is derived and never recorded. There is no `auth` field in the marketplace configuration: a registry uses SSH exactly when `@thetis/host-grants` holds a repository key for its url, so the card shows the key itself and cannot claim one that is gone. The key is the installation's, not a person's: it lives with the system userspace, the system fence's ssh-agent offers it for that repository and no other, and an install from the registry is fetched there and copied to the person. Every write sends the whole `registries` list through `config.set` at the system layer, the same path an extension page's **Configure** takes for a person, and the control panel's **Settings** tab on an extension's page for the system layer, and the marketplace service restarts on the change and refreshes from the new list. The command line has the same keys: `thetis repo-key generate <url>`.

**Ahead, and publishing.** The three kinds of behind all say what this installation is missing. There is a fourth thing to say, and it runs the other way: whoever maintains a package is also running it, from the same checkout every fence loads, so a version bump is live for them the moment it lands while the registry every other installation reads still holds the old one. `@thetis/marketplace`'s `ahead` names both forms of that -- a registry holding an older version, and a package no registry lists at all -- and the row carries it as `ahead`. The badge is `0.3.0 here, 0.2.0 published`, on the page's Details tab (a package no registry lists has no badge at all, only the Details row); a store card does not carry it, because it is the maintainer's business and not the person's. The two carry different tones on purpose: a package the index does not carry is dim, because it is a quiet fact and on the machine of whoever maintains these packages it is true of nearly all of them at once, and a gallery of amber says nothing; a version here that is past what a registry holds is a warning, because that is a gap between what this installation runs and what anybody else can get. **Not `never published`**, which is a claim the index cannot support: the index is built from the registries this installation mirrors, so its silence is a fact about what is mirrored here and not about the world, and a package can sit in a registry nobody here trusts. `thetis packages outdated` prints that same sentence, and so does the control panel's table, so one package does not read three ways in three places. The page's facts carry it in full: a **published** row reading `0.2.0 in thetis — 0.3.0 is what is here`, or `not in any registry`. A fork is left out of all of this: it is a private copy with a fork badge of its own, not work waiting to be shared.

**The index and the targets are two lists.** `ahead` reads the marketplace *index*, which covers the registries `@thetis/marketplace` mirrors; a publish goes to one of `@thetis/package-publish`'s *targets*, and nothing says the two overlap. Publish to a target this installation does not mirror and the index stays silent for ever -- so the index's silence is said as the fact about the index that it is, and the one thing that knows better is this workspace's own record. `publish_targets` asked **about a package** answers `record` per target, `{ published, publishedAt, removed, removedAt, latest, commit }`, where `latest` is `published`, `removed` or null; `publishRecord` in `ui/badges.js` reads it and takes the later act across the targets. It is first-hand -- the person published it from here -- and it is about *that* package, which the per-target `lastPublish` and `lastRemoval` are not: those say what last happened at a target whatever the package was, and reading one for the other is a bug that looks right until the next publish of anything else overwrites the key. `publishRecord` refuses an answer that was not fetched for this package at all, so the cheap call cannot be read as the expensive one.

It is said in the page's **published** row and not in a badge: `0.2.0 to solo · 4 min ago, by this space's own record. No registry here lists it.`, or `taken out of solo` when a removal is the later act, or, when the record was asked and has nothing, `no registry here lists it, and nothing has gone from here to a target yet`. A badge is a summary of state and has to mean the same thing wherever it is read, and the gallery card cannot have the record: asking about a package clones or fetches every target, which is one such round trip per card. So the badge is the index's statement everywhere, and the page -- which is about one package and can afford the question -- says the rest underneath it. The page asks it in two phases for the same reason: the cheap call draws the Publish block, and the per-package one goes out after the page is drawn and fills in that one line, so nothing waits on a fetch and a failure leaves the index's own sentence standing, which is true.

**Publish** is the action that closes that gap, and the only one in the product that changes what other installations receive. It is a soft dependency on `@thetis/package-publish`: nothing here imports it, nothing declares it, and where it is not installed or has no `targets` configured the block is simply not drawn and nothing throws. Where it is, the page shows a registry picker (only when more than one target is configured), a version choice -- *as it is — 0.3.0*, or a patch, minor or major bump, defaulting to *as it is* whenever this copy is already ahead of what is published -- and a **Publish to \<registry\>** button. There is no free-text version box: a box asks a person to do semver arithmetic in their head and then trusts that they did it right. Clicking runs `publish_package` with `dryRun` first, which does everything except the commit and the push, and fills the confirm popover from what it reports: the package at the version that would be published, the target and its url, `0.2.0 → 0.3.0` or "the first version that registry would hold of it", the branch, and one sentence saying that everyone mirroring that registry gets it on their next refresh, that a published version is not taken back, and that only this package's own directory is committed. A refusal -- a version that does not move past the target, a package that will not build -- arrives as a toast before the person has agreed to anything. Only on confirm does the same call go again without `dryRun`.

**A fork's publish is two acts, so the page asks which.** A package carrying `thetis.forkedFrom`, published to a target that already holds that origin and does not yet hold the fork, comes back from the dry run with the blocker `ambiguous-fork` -- because the publish could be the change becoming the next version of the package it was forked from, or the fork becoming a package of its own, apart from that one from here on. The popover does not open. The panel draws the refusal's own sentence and then the two acts, worded as what each does rather than as the flag it sends: **Make it the next version of \<origin\>** and **Make it a package of its own**. `blocker.details` carries `{ origin: { dir, name, version }, fork: { name, version } }`, so both are drawn from fields and not from the prose.

Each act carries its own version control, under it rather than above the pair, because the versions are different questions. As its origin, the version is the origin's next one, measured against what the target holds for the origin, and the fork's own `0.1.0-fork.1` is never a candidate -- so that control offers a patch, a minor or a major step and no "as it is". As itself, the version is the fork's own line, the version on disk included. The numbers are never worked out here: a step is asked for, the dry run is run again with the `as` that was pressed, and what it reports is what the confirm shows. While the question is up the plain Publish row stands down -- its version belongs to neither answer -- and changing the target asks the question again.

The answer is not kept anywhere. The gate fires while the target holds the origin and not this fork, so the registry is what remembers: once a fork is in it under its own name a publish has one reading left and no blocker arrives. On a successful as-origin publish the answer's `fork` says the person's own copy was not rewritten, and the toast says so beside the result -- `@thetis/exa@0.0.10 is in thetis (4f1c2ab). Your copy is still @dev/exa-mine 0.0.9-fork.1, a fork.` -- because that is the one thing somebody would otherwise assume moved, and assuming it wrongly means believing their own workspace changed when it did not.

**Taking a package back out.** **Take out of \<registry\>** sits under the Publish row, not in it: it is the opposite act and the only one here that takes something away from everybody else, and it must not sit a button's width from the thing it undoes by accident. It is drawn only where `publish-targets` says `canRemove`, which is read off the publishing package's manifest. It runs `unpublish_package` with `dryRun` first, exactly as Publish does, so the confirm names the version the registry is actually holding and a removal of something no registry holds is a sentence read before anything is agreed: the package at the version held, the target and its url, the directory and how many files, the branch. The note does not paraphrase the difficult half away -- *It leaves the marketplace index at the next refresh, so nobody installs it again. Every installation that already has it keeps it, goes on running it, and is not told. Nothing in the product puts it back.* -- and in the checkout case it adds that the directory goes from the checkout too, because there the source and the registry are the same directory. The toast afterwards says the same second half again, in the warn tone: it worked, and the sentence it worked into has to be read. A removal's dry run can report the same branch gates a publish's does; they are drawn as reasons with nothing to tick, because nothing rides along with a removal from this page.

**Passengers.** In the case this was built for, the checkout *is* the registry repository, so a publish pushes the branch and any commit already on it rides along, even though the publish's own commit is scoped to one directory. That is the maintainer's ordinary state: work committed across several packages as they went. The publishing package refuses and names them, and a dry run reports the same rows in `blockers[].details` instead of refusing, already sorted into `{ blocked, nameable }`, each row `{ dir, files, package, version, holds, holdsName, moved, publishable, reason, problem }` (a bare list of rows is read too, and a blocker whose `details` is a list of paths -- staged files -- names no package and contributes none). When that comes back, the popover does not open at all. The page draws a panel under the Publish row instead: every blocker's own sentence, whole, then a row per package. `publishable` is the whole decision. A package whose version has gone past what the registry holds can be published in its own right, so it is a **tick**; one that cannot be published can never be named, so it is a **line in the warn colour**, drawn first, saying why -- its `problem` when the manifest is unsound, otherwise the two versions -- and that it cannot ride along either, and while one of those is there **Publish is disabled** -- no amount of ticking makes that publish go, and a person who cannot publish needs to see why rather than press a button that will refuse. Nothing is ever ticked on their behalf. Pressing Publish again re-runs the dry run with `with` set to what they ticked; ticks survive the redraw, a tick for a row that is no longer offered is dropped, and changing the target or the version clears the panel, because that is a different question. When it comes back clean the confirm popover opens with an **also publishing** row naming each passenger -- names, never a count, since a person agreeing to publish somebody else's work reads the names or they have agreed to nothing -- and the toast names them again afterwards.

The facts also carry **last publish** — `@thetis/exa@0.1.0 to thetis · 4 minutes ago` — one row per configured target that has a record, labelled `last publish to <target>` when more than one target has one, and absent without a word when there is none. Beside it, and never folded into it, **last removal** — `@alice/hello@0.2.0 out of thetis · a minute ago` — so a target whose last act was a removal cannot read as though it last saw a publish. The publishing package keeps the two under two keys for exactly that reason. It names the package, because the record is the last publish *to that target*, whatever it was of, and on a given package's page that is very often some other package. It comes from `publish_targets`, out of the publishing package's own store: a publish is not a journal act, because the kernel's journal is the kernel's account of what the kernel did and there is no seam for a package inside a fence to append to it — rightly, since a log anything may write into is a log nobody can lean on.

The tool is reached through `env.invokeTool`, the same seam a harness runs a model's tool call through: the reference (`package`, `export`, `name`) is read off the installed manifest rather than written down here, and the configuration passed with it is `env.kernel.config.effective("@thetis/package-publish")` -- a fence is one person's authority, so a package in it may load another's configuration, exactly as the gateway runs another package's UI commands as the person. `@thetis/package-publish` also exports its library, so an `import()` in the same fence would reach the same code; `invokeTool` is used instead because it is the only one of the two that runs that code under *that package's* env. `env.storage` is namespaced by package, and the publish record lives in the publishing package's namespace: an import here would read this package's store and find nothing.
