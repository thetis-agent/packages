# @thetis/ui-marketplace

The Marketplace place of the web gateway: a gallery of what is installed here, what the installation ships, and what the registries offer, and one page per package with its README, its facts, what it brings, and the actions the person's role allows. It is a `ui` package with no build step; its one dependency is the `@thetis/marketplace` library, for reading the index and the README copies. Its browser modules run in the page; its commands run inside the person's own fence, where `@thetis/gateway-web` calls them as the person. Every person gets it by default.

## What it provides

The manifest declares `type: "ui"` and a `ui` block with `dir: "ui"`, `entry: "index.js"` and `style: "index.css"`.

| Slot | Id | Label | Order | Hint |
|---|---|---|---|---|
| `places` | `marketplace` | Marketplace | 20 | What the registries offer, and what is installed here |

Twenty-eight commands. The first fifteen may be sent by any signed-in person and work on the person's own packages, and the catalog of system packages on disk, through `env.kernel.packages`, their own configuration layer through `env.kernel.config`, their own fence through `fence.reload`, or -- for the three publishing verbs -- another installed package's tool through `env.invokeTool`; the last thirteen carry `role: "admin"` and go through `env.kernel.operator.call`. Seven of those are the Registries page's, in `lib/registries.js`.

| Verb | Export | Who | What it does |
|---|---|---|---|
| `search` | `search` | anyone | `{ q?, type? }`. The rows -- installed first, then the system packages on disk the person does not have (`kernel.packages.catalog`, when the kernel has it), then the registries' offers -- narrowed through the index's search; a row the index does not carry is matched on its name, type and description. Answers the index's facts, the rows, and who is asking. |
| `show` | `show` | anyone | `{ name }`. One row with its README copy, or `null` when no registry holds one, and `assets`: the images the README shows, as `{ [path]: { type, data } }`, as many as fit under the gateway's answer cap. |
| `install` | `install` | anyone | `{ source }`. `kernel.packages.install` into the person's own userspace: a system package by name, which the kernel allows anyone; anything else by its pinned registry source. |
| `remove` | `remove` | anyone | `{ name }`. `kernel.packages.uninstall`. The files stay. |
| `delete` | `del` | anyone | `{ name }`. `kernel.packages.delete`: the package and its files under `packages/`. The kernel allows it only for the person's own scope. |
| `update` | `update` | anyone | `{ name }`. Installs the newer pinned source the registry holds. Refused when the package is not installed or not behind. |
| `unfork` | `unfork` | anyone | `{ name }`. `kernel.packages.unfork`: the userspace goes back to the package this fork was copied from. The fork's files are kept -- `delete` is what removes them. When the fork is the gateway serving the page, this answer is lost with it; the page treats that as the success and waits for the package that took its place. |
| `publish-targets` | `publishTargets` | anyone | `{ package? }`. Where this workspace may publish. Answers `{ available, canRemove, targets, error? }`, and `available: false` -- never a refusal -- when `@thetis/package-publish` is not installed here or has no target configured, which is most installations. `available` is decided from that package's effective configuration before any tool runs, so a page that will not offer Publish pays nothing for asking; `canRemove` is whether that package declares `unpublish_package`, read off the same manifest, so a publishing package from before removal existed draws no button for it. With `package`, the tool also reports what each target holds for it and, in `record`, what this person's own history says about *that package* at that target -- which costs a clone or a fetch of every target, so the page asks it only where it could change what a row says. Each target row carries `lastPublish` and `lastRemoval` out of that package's own store whether or not a package was named; those are the other question, what last happened at this target whatever it was of. |
| `publish` | `publish` | anyone | `{ name, to?, bump?, version?, as?, with?, dryRun? }`. Publishes one package to one registry through `@thetis/package-publish`'s `publish_package`, or, with `dryRun`, reports what that would do without committing or pushing. `bump` is `patch`, `minor` or `major`; give a bump or a version, not both, and neither publishes the version already on disk. `with` is the list of packages being published deliberately alongside this one; a name that is not a package name, the package itself, or the same name twice is refused before the tool is asked, and no passengers is no key at all rather than an empty list. `as` is `origin` or `itself` and is only ever sent for a fork: which of the two publishes this one is. A refusal is thrown and its sentence stands alone in a toast. |
| `unpublish` | `unpublish` | anyone | `{ name, to?, with?, dryRun? }`. Takes one package out of one registry through `unpublish_package`: the directory is deleted, committed and pushed. The name is the one the registry holds it under, so it need not be installed here. With `dryRun` it reports what would go without committing anything, which is where the confirm's facts come from. |
| `config-show` | `configShow` | anyone | `{ name }`. `kernel.config.show`: the person's own layer of an installed package, every key's state, secrets redacted. |
| `config-list` | `configList` | anyone | `kernel.config.show` over every installed package, folded to `[{ package, summary, broken }]` for the gallery; a package the kernel cannot report on is left out. |
| `config-set` | `configSet` | anyone | `{ name, key, value }`. `kernel.config.set` at the person's own layer. `value` is any JSON but never null or undefined: removing a value is `config-unset`. The value is passed through and never appears in a message. The kernel refuses a key declared `scope: "system"`. |
| `config-unset` | `configUnset` | anyone | `{ name, key }`. `kernel.config.unset`. |
| `fence-reload` | `fenceReload` | anyone | No arguments. `fence.reload` for `env.user`, which the kernel allows anyone for their own id. The fence closes and opens again on the code on disk now: this is what puts a version the workspace has not loaded into service. Answers `{ user, services }`. |
| `unmark-everyone` | `unmarkEveryone` | admin | `{ name }`. `packages.unmarkEveryone`: a system package stops being everyone's default. New people are no longer seeded with it; everyone who has it keeps it. The kernel refuses a name the configuration or a promotion made everyone's, and says what to edit instead. |
| `install-everyone` | `installEveryone` | admin | `{ source }`. `packages.installEveryone`: a system package, sent by name, is marked as everyone's default and linked into every person; anything else is installed for the admin and promoted. The toast names anyone the kernel left alone because they hold a fork of the package, and is a warning rather than a success when it did: "installed for everyone" must not be read as everyone when it was not. |
| `install-for` | `installFor` | admin | `{ user, source }`. `packages.install` for that person. |
| `remove-for` | `removeFor` | admin | `{ user, name }`. `packages.uninstall` for that person. |
| `promote` | `promote` | admin | `{ user, name }`. `packages.promote`: a person's package becomes the default for everyone under `@thetis`. |
| `people` | `people` | admin | The people an admin may install for, without the system user. |
| `registries` | `registries` | admin | The Registries page in one answer: `{ registries, orphans, source, updatedAt, keysError }`. Each registry is `{ name, url, auth, key, keyable, deployKeysUrl, error, commit }`: the `@thetis/marketplace` `registries` key as `config.show` reports the system layer, `auth` `ssh` or `none` from whether `host.grants.repoList` holds a key for that url (`sameRepository`), `key` the public part of that key (`repo`, `alias`, `present`, `publicKey`, `fingerprint`, the number of `hosts`), `keyable` whether the url is a hosted one a key can be held for, `deployKeysUrl` GitHub's deploy keys page for the repository or null, and `error`/`commit` the index's word on the last refresh of that name. `orphans` are keys whose repository no registry names. `source` is the layer the list came from, `default` until an admin writes one. When host-grants cannot answer, the registries are still listed, with `keysError`. |
| `registry-add` | `registryAdd` | admin | `{ url, name?, auth?, privateKey? }`. `auth` is `none` (the default), `generate` (`host.grants.repoKeygen { repo }`) or `import` (`host.grants.repoImport { repo, privateKey }`). The key is made first, so a refused key writes nothing; then the list is written whole with `config.set { name: "@thetis/marketplace", key: "registries", value }`. `name` defaults to `slugOfUrl(url)`. A name or a repository already listed is refused, and so is a key for a url that is not hosted. Answers the new name, the key, the deploy keys link and the whole section. |
| `registry-edit` | `registryEdit` | admin | `{ name, newName?, url? }`. Renames a registry or re-points it; another spelling of the same repository keeps its key, but a registry holding a key cannot move to another repository until the key is revoked. |
| `registry-remove` | `registryRemove` | admin | `{ name, keepKey? }`. Writes the list without it, then `host.grants.repoRevoke { repo, keepKey }` for its key, unless another registry still names that repository. |
| `registry-key` | `registryKey` | admin | `{ name, auth: "generate" \| "import", privateKey? }`. Gives a listed registry a key, for the url the configuration holds -- the browser never names the url of a key operation. |
| `registry-key-revoke` | `registryKeyRevoke` | admin | `{ name, keepKey? }`, or `{ repo, keepKey? }` for a key no registry names, which must be one host-grants holds. `host.grants.repoRevoke`. |
| `registry-test` | `registryTest` | admin | `{ name }`. `host.grants.repoTest { repo }`: `git ls-remote` on the host with that key and no other. Answers `{ name, ok, head, error }`, `error` being git's own words. |

Each answers `{ data }`; a refusal is a thrown error, which the gateway answers as `400 { error }`. The gateway answers `403` to an admin verb from a user before the package's code runs, and the kernel refuses an operator method from a fence whose user is not an admin, with one exception it allows anyone: `fence.reload` naming the caller's own id, which is what `fence-reload` sends.

## Use

**Marketplace** in the sidebar's ≡ menu, after **Control panel**, opens the place in the main pane. Escape or the close button returns to the conversation.

When several registries offer the same package, the gallery takes the newest version, keeping the configured registry order for a tie. Its version, source and README come from that same offer.

**Three facts, said apart.** A row used to carry one word, `scope`, for what are three separate things, and that is how **Only me** came to sit on a package shipped with the installation and **Available** on one a person could not install. Now `system` says whose the package is: the installation's, shipped in the checkout or promoted into it, linked already built, and open to anyone by name -- the kernel's `install` takes a `@thetis/<name>` from any signed-in person, because the installation vouched for the code by shipping it and the link runs in the person's own fence. `installed` says whether it is in this person's workspace. `everyone` says whether every person gets it by default, and `everyoneBy` who decided that: `config` (the `systemPackages["*"]` list), `promoted`, or `marked` (an admin's mark, the only one a page can take back). A registry's offer that is also on disk here -- which on an installation whose registry is the repository the checkout ships is nearly every offer -- is one row, a system row, so an install of it is a link and never a clone.

**The gallery** has a search box, one chip per package type, a note on the index (how many packages are in your workspace and how many are system packages; which registries, when refreshed, how many packages; or that there is no index yet), and a card per package: the name, description, version, type and registry, and the badges **System** or **System · everyone** (whose it is, and whether every person gets it), **Mine** for a package of your own scope, or `from <registry>` for an offer that is not on disk here; **Installed** when it is in your workspace; `fork of …`, `update to <version>`, `reload to <version>` or `identical to @thetis/gateway-web 0.2.0`, `0.3.0 here, 0.2.0 published` or `no registry here lists it`, and the benchmark badge. Installed packages come first. An installed package whose configuration is missing something carries the kernel's one sentence about it in red, from one `config-list` call after the rows. Clicking a card opens the package's page. The query is kept, so coming back from a page shows the same list.

**Registries**, for admins, is a button at the end of the gallery's toolbar and a page of its own (the place opened with `{ view: "registries" }`), with the crumb **Marketplace › Registries**. The button is drawn only where `ext.can("registries")`, which is the gateway saying the person's role clears the admin verbs; the verbs themselves answer 403 to anybody else and the kernel refuses the operator calls from a fence that is not an admin's, so hiding it is manners and not the lock. One card per configured registry, the shipped `thetis` one included and editable like any other: the name, the url, a badge for its authentication -- `no authentication`, `SSH key`, or `SSH · key missing` when the key file is gone from the host -- and `refresh failed` with git's words under **Refresh** when the index says the last refresh of that registry failed, or `Mirrored at <commit>.` when it did not. **Edit** renames or re-points it. **Remove** asks first, and when the registry has a key the popover carries a tick, *keep the key file on the host*; unticked, the key is revoked and its file deleted.

A registry without a key says it is read without credentials and offers **Add a key**: *Generate a key* (the host makes an ed25519 key for this repository) or *Paste a private key* (a deploy key that already exists, sent once and never drawn again). **Add registry** at the top opens the same choice under *Authentication: None | SSH key*, with the url and an optional name (the url's last segment when empty). Once a key exists the card shows its fingerprint, the public half in a read-only box with **Copy**, the line *Add this as a read-only deploy key* -- a link to the repository's deploy keys page when the host is github.com, worked out on the server, since the page parses no urls -- and **Test**, which answers `read` and the HEAD commit, or `refused` and git's own error. **Revoke key** takes the key away with the same keep-the-file tick. A key held for a repository that no registry names any more is listed under **Keys without a registry**, with **Revoke**, rather than left unseen.

Authentication is derived and never recorded. There is no `auth` field in the marketplace configuration: a registry uses SSH exactly when `@thetis/host-grants` holds a repository key for its url, so the card shows the key itself and cannot claim one that is gone. The key is the installation's, not a person's: it lives with the system userspace, the system fence's ssh-agent offers it for that repository and no other, and an install from the registry is fetched there and copied to the person. Every write sends the whole `registries` list through `config.set` at the system layer, the same path the control panel's **Package settings** takes, and the marketplace service restarts on the change and refreshes from the new list. The command line has the same keys: `thetis repo-key generate <url>`.

**A package page** has the crumb **Marketplace › name** back to the gallery. On the left, the README copy rendered by the shell's markdown, or "This package has no README." A local image the README shows (`![alt](bench/x/chart.svg)`) is drawn from the copy `show` sent, as a `data:` URL; one the answer does not carry shows as its alt text. On the right, a card with the badges, the description, the facts (installed version and commit, the registry's tip, the type, the license, forked from, replaces, source, and `loaded` — `0.2.1 in your workspace, 0.2.2 on disk: a reload applies it` — for the reload case), what the package brings as pills (tools, steps by phase, service, keywords, benchmark suites), and the actions the state and the role allow. For anyone, one pair: **Install** and **Remove**. There is no "for me": the two act on your workspace and nothing else, and the popover says what kind of install this is -- a system package is linked already built and is over at once, a registry's offer is cloned and built in your own space and takes a minute -- and what the package's type brings, from `whatItBrings`: a skill pack's skills are offered to your agent from the next turn, a tool's tools likewise, a loader's steps run in your turns, a service starts at once, a ui package's places are on the page the next time it loads. A host package and a storage driver have no Install at all; the hint says why (`NOT_INSTALLABLE`). Remove on a system package says it leaves your workspace only, that the installation keeps its copy and Install puts it back, and, when it is everyone's default, that it stays so for everyone else. Then **Update to <version>**, **Reload my workspace** or **Go back to <origin>**, and **Delete** for a package of your own scope. For admins, after the person's own actions and never in place of them: on a system package, **Make it the default for everyone** or, when it is one already, **Stop it being the default** -- drawn only when `everyoneBy` is `marked`; a default the configuration or a promotion made is not the page's to undo, and the hint says where it is undone instead of drawing a button that would refuse; on a registry's offer, **Install for everyone**, which installs it for the admin and promotes it into a system package; on a package of the admin's own, **Make it the default for everyone**, which promotes it; and **Install for <person>** from a picker, for anything that is not already everyone's. Every action sits behind a confirm popover that names the package, where it comes from, whom it is for, and what happens next. Nothing is sent until the person confirms. The facts carry the same three things in full: **state** (`in your workspace` or not), **system** (`everyone's default · by the installation's configuration`, `· promoted`, `· marked by an admin`, or `optional: each person installs it`), and **owner** `you` for your own. There are three kinds of behind, and the page says which one this is. A package installed from a registry whose pin is older than the index offers **Update to <version>**, an install of the newer commit. A package shipped with the service is a link into the checkout, so its files are installed the moment they land and nothing is behind any registry: what the workspace is running is the version its fence read when it opened, and the page offers **Reload my workspace**, whose confirm says that the fence closes for a second, every open shell session in it ends, and the page reconnects on its own. That request is expected to be lost, because it closes the fence answering it, so the page waits for the new workspace rather than reporting a failure, and says what to do if it never answers. A fork is behind in a third way: the package it was copied from goes on being fixed and the copy does not. The card says so -- `fork of @thetis/gateway-web 0.1.1 · 0.2.0 is shipped now`, or the stronger `identical to @thetis/gateway-web 0.2.0, which is shipped` when the copy changed nothing at all, with `· everyone else gets that one` on the end when the package it was copied from is the house default -- an admin cannot make that default this person's, because the kernel refuses to install a package over somebody's fork of it, so the badge is the only place the decision reaches them -- the facts carry a **shipped now** row beside **forked from**, and the page offers **Go back to @thetis/gateway-web**. Its confirm says that the fork's files stay where they are, and, when the fork is a gateway, that this page is served by the package being replaced and will go quiet for a second. That request is lost the same way a reload's is, and is waited out the same way. Deleting the files is still **Delete**, which the person can reach once the shipped package is back. An installed package also has **Configure**: the card says the kernel's sentence when the package is missing something, and the button opens the configuration form under the README, on the person's own layer. A row per key says its state and where the value came from, a secret is a write-only box that says `set` or `not set`, a key declared for admins is read-only, **Clear** removes what this layer holds, and **Save** sends one `config-set` per key that changed. The form is `ui/config-form.js`, the same file `@thetis/ui-admin` carries for the system layer.

**Ahead, and publishing.** The three kinds of behind all say what this installation is missing. There is a fourth thing to say, and it runs the other way: whoever maintains a package is also running it, from the same checkout every fence loads, so a version bump is live for them the moment it lands while the registry every other installation reads still holds the old one. `@thetis/marketplace`'s `ahead` names both forms of that -- a registry holding an older version, and a package no registry lists at all -- and the row carries it as `ahead`. The badge is `0.3.0 here, 0.2.0 published` or `no registry here lists it`, on the gallery card and on the page. The two carry different tones on purpose: a package the index does not carry is dim, because it is a quiet fact and on the machine of whoever maintains these packages it is true of nearly all of them at once, and a gallery of amber says nothing; a version here that is past what a registry holds is a warning, because that is a gap between what this installation runs and what anybody else can get. **Not `never published`**, which is a claim the index cannot support: the index is built from the registries this installation mirrors, so its silence is a fact about what is mirrored here and not about the world, and a package can sit in a registry nobody here trusts. `thetis packages outdated` prints that same sentence, and so does the control panel's table, so one package does not read three ways in three places. The page's facts carry it in full: a **published** row reading `0.2.0 in thetis — 0.3.0 is what is here`, or `no registry here lists it`. A fork is left out of all of this: it is a private copy with a fork badge of its own, not work waiting to be shared.

**The index and the targets are two lists.** `ahead` reads the marketplace *index*, which covers the registries `@thetis/marketplace` mirrors; a publish goes to one of `@thetis/package-publish`'s *targets*, and nothing says the two overlap. Publish to a target this installation does not mirror and the index stays silent for ever -- so the index's silence is said as the fact about the index that it is, and the one thing that knows better is this workspace's own record. `publish_targets` asked **about a package** answers `record` per target, `{ published, publishedAt, removed, removedAt, latest, commit }`, where `latest` is `published`, `removed` or null; `publishRecord` in `ui/badges.js` reads it and takes the later act across the targets. It is first-hand -- the person published it from here -- and it is about *that* package, which the per-target `lastPublish` and `lastRemoval` are not: those say what last happened at a target whatever the package was, and reading one for the other is a bug that looks right until the next publish of anything else overwrites the key. `publishRecord` refuses an answer that was not fetched for this package at all, so the cheap call cannot be read as the expensive one.

It is said in the page's **published** row and not in a badge: `0.2.0 to solo · 4 min ago, by this workspace's own record. No registry here lists it.`, or `taken out of solo` when a removal is the later act, or, when the record was asked and has nothing, `no registry here lists it, and nothing has gone from here to a target yet`. A badge is a summary of state and has to mean the same thing wherever it is read, and the gallery card cannot have the record: asking about a package clones or fetches every target, which is one such round trip per card. So the badge is the index's statement everywhere, and the page -- which is about one package and can afford the question -- says the rest underneath it. The page asks it in two phases for the same reason: the cheap call draws the Publish block, and the per-package one goes out after the page is drawn and fills in that one line, so nothing waits on a fetch and a failure leaves the index's own sentence standing, which is true.

**Publish** is the action that closes that gap, and the only one in the product that changes what other installations receive. It is a soft dependency on `@thetis/package-publish`: nothing here imports it, nothing declares it, and where it is not installed or has no `targets` configured the block is simply not drawn and nothing throws. Where it is, the page shows a registry picker (only when more than one target is configured), a version choice -- *as it is — 0.3.0*, or a patch, minor or major bump, defaulting to *as it is* whenever this copy is already ahead of what is published -- and a **Publish to \<registry\>** button. There is no free-text version box: a box asks a person to do semver arithmetic in their head and then trusts that they did it right. Clicking runs `publish_package` with `dryRun` first, which does everything except the commit and the push, and fills the confirm popover from what it reports: the package at the version that would be published, the target and its url, `0.2.0 → 0.3.0` or "the first version that registry would hold of it", the branch, and one sentence saying that everyone mirroring that registry gets it on their next refresh, that a published version is not taken back, and that only this package's own directory is committed. A refusal -- a version that does not move past the target, a package that will not build -- arrives as a toast before the person has agreed to anything. Only on confirm does the same call go again without `dryRun`.

**A fork's publish is two acts, so the page asks which.** A package carrying `thetis.forkedFrom`, published to a target that already holds that origin and does not yet hold the fork, comes back from the dry run with the blocker `ambiguous-fork` -- because the publish could be the change becoming the next version of the package it was forked from, or the fork becoming a package of its own, apart from that one from here on. The popover does not open. The panel draws the refusal's own sentence and then the two acts, worded as what each does rather than as the flag it sends: **Make it the next version of \<origin\>** and **Make it a package of its own**. `blocker.details` carries `{ origin: { dir, name, version }, fork: { name, version } }`, so both are drawn from fields and not from the prose.

Each act carries its own version control, under it rather than above the pair, because the versions are different questions. As its origin, the version is the origin's next one, measured against what the target holds for the origin, and the fork's own `0.1.0-fork.1` is never a candidate -- so that control offers a patch, a minor or a major step and no "as it is". As itself, the version is the fork's own line, the version on disk included. The numbers are never worked out here: a step is asked for, the dry run is run again with the `as` that was pressed, and what it reports is what the confirm shows. While the question is up the plain Publish row stands down -- its version belongs to neither answer -- and changing the target asks the question again.

The answer is not kept anywhere. The gate fires while the target holds the origin and not this fork, so the registry is what remembers: once a fork is in it under its own name a publish has one reading left and no blocker arrives. On a successful as-origin publish the answer's `fork` says the person's own copy was not rewritten, and the toast says so beside the result -- `@thetis/exa@0.0.10 is in thetis (4f1c2ab). Your copy is still @dev/exa-mine 0.0.9-fork.1, a fork.` -- because that is the one thing somebody would otherwise assume moved, and assuming it wrongly means believing their own workspace changed when it did not.

**Taking a package back out.** **Take out of \<registry\>** sits under the Publish row, not in it: it is the opposite act and the only one here that takes something away from everybody else, and it must not sit a button's width from the thing it undoes by accident. It is drawn only where `publish-targets` says `canRemove`, which is read off the publishing package's manifest. It runs `unpublish_package` with `dryRun` first, exactly as Publish does, so the confirm names the version the registry is actually holding and a removal of something no registry holds is a sentence read before anything is agreed: the package at the version held, the target and its url, the directory and how many files, the branch. The note does not paraphrase the difficult half away -- *It leaves the marketplace index at the next refresh, so nobody installs it again. Every installation that already has it keeps it, goes on running it, and is not told. Nothing in the product puts it back.* -- and in the checkout case it adds that the directory goes from the checkout too, because there the source and the registry are the same directory. The toast afterwards says the same second half again, in the warn tone: it worked, and the sentence it worked into has to be read. A removal's dry run can report the same branch gates a publish's does; they are drawn as reasons with nothing to tick, because nothing rides along with a removal from this page.

**Passengers.** In the case this was built for, the checkout *is* the registry repository, so a publish pushes the branch and any commit already on it rides along, even though the publish's own commit is scoped to one directory. That is the maintainer's ordinary state: work committed across several packages as they went. The publishing package refuses and names them, and a dry run reports the same rows in `blockers[].details` instead of refusing, already sorted into `{ blocked, nameable }`, each row `{ dir, files, package, version, holds, holdsName, moved, publishable, reason, problem }` (a bare list of rows is read too, and a blocker whose `details` is a list of paths -- staged files -- names no package and contributes none). When that comes back, the popover does not open at all. The page draws a panel under the Publish row instead: every blocker's own sentence, whole, then a row per package. `publishable` is the whole decision. A package whose version has gone past what the registry holds can be published in its own right, so it is a **tick**; one that cannot be published can never be named, so it is a **line in the warn colour**, drawn first, saying why -- its `problem` when the manifest is unsound, otherwise the two versions -- and that it cannot ride along either, and while one of those is there **Publish is disabled** -- no amount of ticking makes that publish go, and a person who cannot publish needs to see why rather than press a button that will refuse. Nothing is ever ticked on their behalf. Pressing Publish again re-runs the dry run with `with` set to what they ticked; ticks survive the redraw, a tick for a row that is no longer offered is dropped, and changing the target or the version clears the panel, because that is a different question. When it comes back clean the confirm popover opens with an **also publishing** row naming each passenger -- names, never a count, since a person agreeing to publish somebody else's work reads the names or they have agreed to nothing -- and the toast names them again afterwards.

The facts also carry **last publish** — `@thetis/exa@0.1.0 to thetis · 4 minutes ago` — one row per configured target that has a record, labelled `last publish to <target>` when more than one target has one, and absent without a word when there is none. Beside it, and never folded into it, **last removal** — `@alice/hello@0.2.0 out of thetis · a minute ago` — so a target whose last act was a removal cannot read as though it last saw a publish. The publishing package keeps the two under two keys for exactly that reason. It names the package, because the record is the last publish *to that target*, whatever it was of, and on a given package's page that is very often some other package. It comes from `publish_targets`, out of the publishing package's own store: a publish is not a journal act, because the kernel's journal is the kernel's account of what the kernel did and there is no seam for a package inside a fence to append to it — rightly, since a log anything may write into is a log nobody can lean on.

The tool is reached through `env.invokeTool`, the same seam a harness runs a model's tool call through: the reference (`package`, `export`, `name`) is read off the installed manifest rather than written down here, and the configuration passed with it is `env.kernel.config.effective("@thetis/package-publish")` -- a fence is one person's authority, so a package in it may load another's configuration, exactly as the gateway runs another package's UI commands as the person. `@thetis/package-publish` also exports its library, so an `import()` in the same fence would reach the same code; `invokeTool` is used instead because it is the only one of the two that runs that code under *that package's* env. `env.storage` is namespaced by package, and the publish record lives in the publishing package's namespace: an import here would read this package's store and find nothing.
