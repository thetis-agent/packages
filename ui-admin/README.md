# @thetis/ui-admin

The admin sections of the web gateway's control panel: People, Models, Mounts, SSH keys, Activity, Workspaces and Overview, plus one settings page per package with configuration under the Packages section, and the commands behind them. It is a `ui` package with no build step and no dependencies. Its browser modules run in the page; its commands run inside the admin's own fence, where `@thetis/gateway-web` calls them as the admin, and each one is one call over the kernel's operator channel. Every person gets the package by default; a user sees none of it, because `api/ui` drops the entries and verbs above the person's role.

## What it provides

The manifest declares `type: "ui"` and a `ui` block with `dir: "ui"`, `entry: "index.js"` and `style: "index.css"`. Every entry and every verb carries `role: "admin"`.

| Slot | Id | Label | Order | Note |
|---|---|---|---|---|
| `panel` | `people` | People | 20 | Who can sign in, and what they may do. |
| `panel` | `models` | Models | 30 | Which model answers by default, and what the providers serve. |
| `panel` | `configuration` | Package settings | 32 | Hangs under the shell's Packages section (`under: "packages"`): one page per package with configuration, named by the package. |
| `panel` | `mounts` | Mounts | 35 | Which host directories are bound into whose space. |
| `panel` | `ssh` | SSH keys | 36 | Which keys each person's workspace may use, and where they may go. |
| `panel` | `activity` | Activity | 40 | What happened: who did what, and when. |
| `panel` | `workspaces` | Workspaces | 45 | What code each workspace is running, and how to put new code into service. |
| `panel` | `overview` | Overview | 50 | How this installation is set up. |

The orders sort the sections after the gateway's built-in Packages section (order 10).

| `config-unset` | `configUnset` | `name`, `key`, `user?` | `config.unset`: removes one key from that layer. |
| `config-reload` | `configReload` | none | `config.reload`: re-reads `thetis.config.json` and the env file; answers `{ changed, restarted }`. |
| `journal` | `journal` | `limit?`, `kind?` | `journal.tail`: the newest rows, 200 by default, at most 1000. |
| `mounts-list` | `mountsList` | `user?` | `host.grants.mountsList`: one person's mounts, or everyone's, each with `present` and `kind`: what the host holds at the path now. |
| `mounts-set` | `mountsSet` | `user`, `mounts` | `host.grants.mountsSet`: replaces that person's list. | `mounts-browse` | `mountsBrowse` | `path?` | `host.grants.mountsBrowse`: the directories under one host path, for the picker. The root without a path. |

| `ssh-set` | `sshSet` | `user`, `ssh` (at most 16 `{ key, hosts? }`) | `host.grants.sshSet`: replaces the person's grants whole. A key is an absolute normalized path, never `/`; hosts a list of known_hosts lines, trimmed and deduplicated; a key listed twice is refused. |
| `ssh-keygen` | `sshKeygen` | `user`, `hosts` (optional lines) | `host.grants.sshKeygen` with `{ key: "/generated", hosts }`: the host package makes the person an ed25519 key of their own, once, and grants it; answers the public half to register. |
| `ssh-import` | `sshImport` | `user`, `name`, `privateKey`, `hosts` (optional) | `host.grants.sshImport`: a pasted private key kept by the host package beside the generated one and granted. The name is `[a-z0-9][a-z0-9._-]{0,63}`; the material must hold a `PRIVATE KEY` line and be under 16 KB; a refusal names the rule and never the text. |
| `ssh-scan` | `sshScan` | `host` (hostname, optional `:port`) | Runs `ssh-keyscan -T 5` inside this fence and answers `{ host, lines }`; anything but a hostname is refused before the shell. |
| `ssh-test` | `sshTest` | `target` (`user@host`, optional `:port`) | Runs `ssh -T -o BatchMode=yes -o ConnectTimeout=10 <user>@<host>` inside the admin's own workspace and answers `{ target, code, output }`; it speaks for the admin's grants only, and only a checked user and host reach the shell. |
| `fence-reload` | `fenceReload` | `user` | `fence.reload`: closes that person's fence and opens it again on the code on disk now. `_system` is a legal target; every other id is checked the way `mounts-set` checks one. Answers `{ user, services }`. |
| `status` | `status` | none | `status`: `{ daemon, restart, workspaces }` — what the daemon and every workspace are running, and whether the code on disk is newer. |
| `restart-request` | `restartRequest` | `reason` | `restart.request`: arms the restart latch. The reason is required, and the latch's own sentence — armed, already armed, or refused — is the answer. |

Only an admin may send any of them. Each checks its arguments first, so a refusal is a plain sentence before the kernel is asked, and answers `{ data }`. The admin's own id comes from `env.user`, never from the arguments. The `host.grants.*` methods are answered by `@thetis/host-grants`, a package of type `host` the host process loads; the kernel only dispatches them, so an edit to that package is live on the next call and no restart is ever needed for the mounts or the keys.

The role is checked three times: the page draws only what `api/ui` listed for the person, the gateway answers `403` to a verb above the person's role before the package's code runs, and the kernel refuses an operator method from a fence whose user is not an admin.

## Use

An admin opens **Control panel** from the sidebar's ≡ menu and finds the seven sections after Packages.

- **People**: a table of everyone with their role, status and since when. An **Add a person** form with id, role and password. Clicking a row opens a card with **Make an admin** or **Make a user**, **Suspend** or **Activate**, **Set password** and **Remove**, each behind a confirm popover. The admin's own row shows a note instead: another admin, or the host, changes that account.
- **Models**: the default model and the models every provider serves, with a filter. Read-only.
- **All workspaces**: the first page under Packages (`ui/fleet.js`), one `fleet` answer drawn as a matrix: a row per package with its version, the registry's word (`current`, `<version> on offer`, `reload to <version>`, `not indexed`) and its configuration (`whole`, `missing something`, `no keys`), then a cell per person with the version that person runs, coloured current, `↻` (the workspace has not loaded the version on disk: the cell shows what it loaded, with the title `loaded 0.2.1, 0.2.2 on disk`), older code, fork (`Y`), broken, or dashed for not installed. Seven tiles above count the fleet's current copies, updates on offer, workspaces to reload, forks in use, broken configurations, workspaces on older code and commits not pushed. The search box, the type chips, Show (everything, drift only, with configuration) and Group by (scope, type, registry) narrow and arrange the rows in the browser. **Update N packages** confirms the list and sends one `package-update` per package. **Reload N workspaces** is the other kind of behind: it confirms a list of the workspaces with what each one has not loaded (`@thetis/skills-hybrid 0.2.1 → 0.2.2`) and sends one `fence-reload` per workspace, the admin's own last, through `reloadWorkspace` in `ui/workspaces.js`, so a reload that closes the fence serving the page is waited for rather than reported as a failure. It is not drawn when every workspace has loaded what is on disk. A row opens that package's page.
- **Workspaces** (`ui/workspaces.js`): the daemon's own card, then a row per workspace saying what code it is running. The Services column is what is actually running, from `status`'s `services`, and a service that failed to start is not in it: it gets a `not running` warning badge instead, with the moment it went down and what it said in the title, from `status`'s `down`. That distinction is the whole point of the pair — the list used to be every installed package that *declares* a service, so a dead one sat here looking exactly like a serving one — and the remedy is the **Reload** control already in the row. A workspace holding a version the files on disk have moved past also lists what it has not loaded — `skills-hybrid 0.2.1 → 0.2.2, tool-groups 0.1.0 → 0.2.0`, from `status`'s `changed`, the scopes dropped for reading and whole in the title — so **Reload** in that row says what it is for, and the confirm repeats it as `applies`.
- **A package's page** (`ui/package-page.js`, one per package under Packages, named by the package): the header carries the name, version, type, scope, the configuration's one sentence (red when broken), a fork's origin, an update on offer or `reload to <version>` when this workspace has not loaded what is on disk, and commits not pushed; a facts line from `package-where` (installed for how many people, loaded in how many workspaces and how many run older code, forks); and the actions Update, Fork, Promote, Reload workspace and Remove, each behind a confirm, each tagged **admin** (needs an admin, acts for everyone) or **yours** (anyone, for their own workspace). Update is not offered for the reload kind of behind, because the copy on disk is installed already and nothing would be fetched; Reload workspace is what applies it, and its confirm names the version it brings. Tabs: **Overview** (`ui/package-overview.js`: the provenance card with a lineage drawing from registry to this copy to a promoted copy with forks hanging off, then source, registry, pin, `loaded` when the workspace is running a version the disk has moved past, forks, what it depends on and what depends on it; the checkout card with the branch, ahead and behind, a two-lane mini graph of the five newest commits touching the package from `package-log`; the where-it-runs card; and the files card), **History** (below), **Configuration** (`mountSettings`, the form at full width with the layer picker), **Where it runs** (`ui/package-where.js`: a person picker whose entries summarise each person, previous and next, the facts for the chosen person — version, whether their workspace runs older code, services, configuration — and the buttons Reload their workspace, Open their layer, Their activity, Remove for them or Install for them; the tab adds a table of everyone), **Activity** (`ui/package-activity.js`: the journal about the package from `package-activity`, with kind chips and a range) and **README** (`ui/package-readme.js`).
- **History** (a package page tab, `ui/package-history.js`): the commits that touched the package from `package-log`, as a lane graph beside the rows: the upstream in the accent, commits not yet pushed in the warn tone curving into it, the pinned commit ringed and the commit the registry index names filled, HEAD outlined. Range (7 d, 30 d, all — all asks for 200) and search filter in the page. A row opens the inspector from `package-commit`: message, author, branch, whether pushed, in the registry and pinned, and the package's files with added/removed bars; Show diff asks `package-diff` for parent→commit, Compare pin ↔ HEAD and Compare with working tree ask it for those two; Push asks `package-push` behind a confirm and reloads.
- **SSH keys**: one person at a time from the picker; their keys as cards from `ssh-list`, each with its name and fingerprint, whether the file is on the host, the public half in a line with **Copy** and the sentence about where it goes (a code host's account, a server's authorized_keys), the hosts the operator vouched for as chips (each removable) with **Add host** (a host to look up, **Scan** through `ssh-scan`, the lines kept as chips), the file's path, and **Revoke**. **New key** and **Import key** open one form at the top: the hosts are optional in both, since a host met for the first time is trusted and remembered in the workspace; Import takes a name and the private key pasted once (`ssh-import`). For the admin's own workspace, **Try a connection** runs `ssh -T` to any `user@host` through `ssh-test` and says what the answer means: let in, reached but refused (register a public key there), not trusted (a changed host key), or not reached. Every change closes that person's fence, which reopens with an agent holding the new list; changing your own keys reopens this page, which waits for its gateway to answer again.
- **Overview**: first the installation itself, then the configuration with secrets hidden. The **Installation** card says where the runtime checkout stands (`main @ 8309ab0`, up to date or `N behind origin/main`, uncommitted changes), where the packages submodule stands against the commit the runtime's upstream pins for it, the Node version, whether the daemon runs the code on disk, how many workspaces run older code, and the last update's record. **Check for updates** reaches the remotes (`update-check` with `fetch: true`) and lists the incoming commits of both checkouts. **Update now**, behind a confirm that says what it pulls and that nothing running changes, starts `update-run` and then polls `update-progress` every two seconds, drawing each step with its state and the running or failed step's output; the update is `@thetis/host-update`'s, on the host: `git pull --ff-only`, `git submodule update`, `npm ci`, `npm run build`. When it is done the card re-reads `status` and offers what puts the new code into service: **Reload N workspaces**, through the same helper the Workspaces section uses, the admin's own last, and **Restart the daemon**, through the same latch, with the reason filled in. Node, the OS packages and the systemd unit are the installer's, and the card says so.

## Tests

`npm test` from the runtime root runs `test/ui-admin.test.js`: each command over a fake `env.kernel.operator.call` (the method and arguments it sends, what it refuses before the kernel is asked, the own-account refusal), the `config-*` verbs (the arguments they pass to `config.*`, what they refuse, and that nothing is written to the console, so no value can be), the card's facts including the reload line, the fleet matrix's pure helpers (`cellState`, `drifts`, `workspacesBehind`, which puts the admin's own workspace last), the form's pure helpers, and the browser modules (they parse, the entry defines `install` and nothing else, `install` registers exactly the seven sections). `test/fleet.test.js` covers the people and fleet commands over a fake operator, the matrix's rows and counts, and a workspace holding a version the disk has moved past (`byUser.loaded`, `behindDisk`, the `reload` row and `stats.reloads`). `packages/gateway-web/test/gateway.test.ts` sends the verbs through a real gateway as an admin and as a user. The browser checklist is `packages/gateway-web/test/BROWSER.md`.
