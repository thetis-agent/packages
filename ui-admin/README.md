# @thetis/ui-admin

The web gateway's control panel beyond Packages: Account, People, Models, Mounts, SSH keys, Activity, Workspaces and Overview, plus one settings page per package with configuration under the Packages section, and the commands behind them. It is a `ui` package with no build step and no dependencies. Its browser modules run in the page; its commands run inside the signed-in person's own fence, where `@thetis/gateway-web` calls them as that person, and most are one call over the kernel's operator channel. Every person gets the package by default. A user sees five sections, each about themselves: their account and password, the models their workspace can call, their own mounts, their own SSH keys, and the journal rows about them. An admin sees all of them, about everyone. `api/ui` drops the entries and verbs above the person's role, and the kernel answers a user's fence only about that user.

## What it provides

The manifest declares `type: "ui"` and a `ui` block with `dir: "ui"`, `entry: "index.js"` and `style: "index.css"`. An entry or verb without a `role` is anyone's; the rest carry `role: "admin"`.

The verbs marked Anyone above carry no role; every other verb is an admin's. Each checks its arguments first, so a refusal is a plain sentence before the kernel is asked, and answers `{ data }`. The person's own id comes from `env.user`, never from the arguments. The `host.grants.*` methods are answered by `@thetis/host-grants`, a package of type `host` the host process loads; the kernel only dispatches them, so an edit to that package is live on the next call and no restart is ever needed for the mounts or the keys.

The role is checked three times: the page draws only what `api/ui` listed for the person, the gateway answers `403` to a verb above the person's role before the package's code runs, and the kernel is the authority on every operator method. From a user's fence it admits only `users.passwd` for their own id with the current password, `journal.tail` narrowed to the rows about them, `host.grants.mountsList` and the ssh exports `@thetis/host-grants` declares a person may call on themselves (with `user` pinned to the caller), and a reload of their own fence; everything else only from an admin's. The browser modules branch on `who.role` to draw a person's own view, but a user who sent another id would still be answered only about themselves.

## Use

Anyone opens **Control panel** from the sidebar's ≡ menu. A user finds Account, Models, Mounts, SSH keys and Activity after Packages; an admin finds all eight sections.

- **Account** (`ui/account.js`, everyone): a card with your id and role, and a **Change password** form (current, new, new again; `type=password` with `current-password` and `new-password` autocomplete). The page checks the new password is not empty and matches its confirmation; a confirm popover says "This signs you out everywhere, this browser included."; on success a toast, then the page goes to `/`, which sends a person with no sign-in to the sign-in page. Your picture is the round button at the bottom of the sidebar, not here.
- **What a user sees in the shared sections.** **Models**: "Models you can use", what their own workspace can call, the default marked and the models of a provider installed in their own workspace marked `yours`; the composer's picker chooses per conversation, and this is the default a new one starts with. **Mounts**: their own mounts, read-only, each in one sentence from what the server found at the path ("Bound read-write at /x", "Not bound: the host has no directory at /x, so your workspace opened without it."), a summary line when any is not bound, and the repair: an admin changes it in Mounts, or on the host runs `thetis mounts remove <id> <path>`. No add form and no directory picker. **SSH keys**: their own keys, with no person picker; New key, Import key, Add host, Try a connection and Revoke all work, each on their own workspace, and a key outside their own key directory says "Granted by an admin; you can revoke it but not re-grant it." **Activity**: "What was done by you or to you", with the kind filter.

- **People**: a table of everyone with their role, status and since when. An **Add a person** form with id, role and password. Clicking a row opens a card with **Make an admin** or **Make a user**, **Suspend** or **Activate**, **Set password** and **Remove**, each behind a confirm popover. The admin's own row shows a note instead: another admin, or the host, changes that account.
- **Models** (as an admin): the default model and the models every provider serves, with a filter. Read-only.
- **All workspaces**: the first page under Packages (`ui/fleet.js`), one `fleet` answer drawn as a matrix: a row per package with its version, the registry's word (`current`, `<version> on offer`, `reload to <version>`, `not indexed`) and its configuration (`whole`, `missing something`, `no keys`), then a cell per person with the version that person runs, coloured current, `↻` (the workspace has not loaded the version on disk: the cell shows what it loaded, with the title `loaded 0.2.1, 0.2.2 on disk`), older code, fork (`Y`), broken, or dashed for not installed. Seven tiles above count the fleet's current copies, updates on offer, workspaces to reload, forks in use, broken configurations, workspaces on older code and commits not pushed. The search box, the type chips, Show (everything, drift only, with configuration) and Group by (scope, type, registry) narrow and arrange the rows in the browser. **Update N packages** confirms the list and sends one `package-update` per package. **Reload N workspaces** is the other kind of behind: it confirms a list of the workspaces with what each one has not loaded (`@thetis/skills-hybrid 0.2.1 → 0.2.2`) and sends one `fence-reload` per workspace, the admin's own last, through `reloadWorkspace` in `ui/workspaces.js`, so a reload that closes the fence serving the page is waited for rather than reported as a failure. It is not drawn when every workspace has loaded what is on disk. A row opens that package's page.
- **Workspaces** (`ui/workspaces.js`): the daemon's own card, then a row per workspace saying what code it is running. The Services column is what is actually running, from `status`'s `services`, and a service that failed to start is not in it: it gets a `not running` warning badge instead, with the moment it went down and what it said in the title, from `status`'s `down`. That distinction is the whole point of the pair — the list used to be every installed package that *declares* a service, so a dead one sat here looking exactly like a serving one — and the remedy is the **Reload** control already in the row. A workspace holding a version the files on disk have moved past also lists what it has not loaded — `skills-hybrid 0.2.1 → 0.2.2, tool-groups 0.1.0 → 0.2.0`, from `status`'s `changed`, the scopes dropped for reading and whole in the title — so **Reload** in that row says what it is for, and the confirm repeats it as `applies`. A workspace with a turn running in it is not reloaded: the kernel refuses and names the session, the row asks whether to cancel the turn and reload, and only a yes sends `force`; the fleet page and the Overview's sweep leave such a workspace alone and say so. A cancelled turn ends as a cancel with what it had said and done kept.
- **A package's page** (`ui/package-page.js`, one per package under Packages, named by the package): the header carries the name, version, type, scope, the configuration's one sentence (red when broken), a fork's origin, an update on offer or `reload to <version>` when this workspace has not loaded what is on disk, and commits not pushed; a facts line from `package-where` (installed for how many people, loaded in how many workspaces and how many run older code, forks); and the actions Update, Fork, Promote, Reload workspace and Remove, each behind a confirm, each tagged **admin** (needs an admin, acts for everyone) or **yours** (anyone, for their own workspace). Update is not offered for the reload kind of behind, because the copy on disk is installed already and nothing would be fetched; Reload workspace is what applies it, and its confirm names the version it brings. Tabs: **Overview** (`ui/package-overview.js`: the provenance card with a lineage drawing from registry to this copy to a promoted copy with forks hanging off, then source, registry, pin, `loaded` when the workspace is running a version the disk has moved past, forks, what it depends on and what depends on it; the checkout card with the branch, ahead and behind, a two-lane mini graph of the five newest commits touching the package from `package-log`; the where-it-runs card; and the files card), **History** (below), **Configuration** (`mountSettings`, the form at full width with the layer picker), **Where it runs** (`ui/package-where.js`: a person picker whose entries summarise each person, previous and next, the facts for the chosen person — version, whether their workspace runs older code, services, configuration — and the buttons Reload their workspace, Open their layer, Their activity, Remove for them or Install for them; the tab adds a table of everyone), **Activity** (`ui/package-activity.js`: the journal about the package from `package-activity`, with kind chips and a range) and **README** (`ui/package-readme.js`).
- **History** (a package page tab, `ui/package-history.js`): the commits that touched the package from `package-log`, as a lane graph beside the rows: the upstream in the accent, commits not yet pushed in the warn tone curving into it, the pinned commit ringed and the commit the registry index names filled, HEAD outlined. Range (7 d, 30 d, all — all asks for 200) and search filter in the page. A row opens the inspector from `package-commit`: message, author, branch, whether pushed, in the registry and pinned, and the package's files with added/removed bars; Show diff asks `package-diff` for parent→commit, Compare pin ↔ HEAD and Compare with working tree ask it for those two; Push asks `package-push` behind a confirm and reloads.
- **SSH keys** (as an admin): one person at a time from the picker; their keys as cards from `ssh-list`, each with its name and fingerprint, whether the file is on the host, the public half in a line with **Copy** and the sentence about where it goes (a code host's account, a server's authorized_keys), the hosts the operator vouched for as chips (each removable) with **Add host** (a host to look up, **Scan** through `ssh-scan`, the lines kept as chips), the file's path, and **Revoke**. **New key** and **Import key** open one form at the top: the hosts are optional in both, since a host met for the first time is trusted and remembered in the workspace; Import takes a name and the private key pasted once (`ssh-import`). For the admin's own workspace, **Try a connection** runs `ssh -T` to any `user@host` through `ssh-test` and says what the answer means: let in, reached but refused (register a public key there), not trusted (a changed host key), or not reached. Every change closes that person's fence, which reopens with an agent holding the new list; changing your own keys reopens this page, which waits for its gateway to answer again.
- **Overview**: first the installation itself, then the configuration with secrets hidden. The **Installation** card says where the runtime checkout stands (`main @ 8309ab0`, up to date or `N behind origin/main`, uncommitted changes), where the packages submodule stands against the commit the runtime's upstream pins for it, the Node version, whether the daemon runs the code on disk, how many workspaces run older code, and the last update's record. **Check for updates** reaches the remotes (`update-check` with `fetch: true`) and lists the incoming commits of both checkouts. **Update now**, behind a confirm that says what it pulls and that nothing running changes, starts `update-run` and then polls `update-progress` every two seconds, drawing each step with its state and the running or failed step's output; the update is `@thetis/host-update`'s, on the host: `git pull --ff-only`, `git submodule update`, `npm ci`, `npm run build`. When it is done the card re-reads `status` and offers what puts the new code into service: **Reload N workspaces**, through the same helper the Workspaces section uses, the admin's own last, and **Restart the daemon**, through the same latch, with the reason filled in. Node, the OS packages and the systemd unit are the installer's, and the card says so.

## Tests

`npm test` from the runtime root runs `test/ui-admin.test.js`: each command over a fake `env.kernel.operator.call` (the method and arguments it sends, what it refuses before the kernel is asked, the own-account refusal), the manifest's role table (which entries and verbs carry no role), `account`, `password-change` (the id is `env.user`, `current` is sent, empties refused), the `models` user branch over `env.kernel.models()`, the mount sentences a user reads (`mountSentence`, `removeCommand`), the `config-*` verbs (the arguments they pass to `config.*`, what they refuse, and that nothing is written to the console, so no value can be), the card's facts including the reload line, the fleet matrix's pure helpers (`cellState`, `drifts`, `workspacesBehind`, which puts the admin's own workspace last), the form's pure helpers, and the browser modules (they parse, the entry defines `install` and nothing else, `install` registers exactly the nine declared entries). `test/ssh.test.js` covers the ssh verbs and the SSH section's pure helpers, `isOwnKey` among them. `test/fleet.test.js` covers the people and fleet commands over a fake operator, the matrix's rows and counts, and a workspace holding a version the disk has moved past (`byUser.loaded`, `behindDisk`, the `reload` row and `stats.reloads`). `packages/gateway-web/test/gateway.test.ts` sends the verbs through a real gateway as an admin and as a user. The browser checklist is `packages/gateway-web/test/BROWSER.md`.
